# 安全模型

本文说明 GameRuntimeLibrary 的信任根、校验顺序、信任边界与已知限制，供部署评审与漏洞报告参考。

## 适用范围

本项目是一个以管理员权限运行的 PowerShell 安装器，负责从厂商官方地址获取安装包并静默安装。安全目标有三个：

1. 不安装来源不明或被篡改的安装包。
2. 不因解压或路径处理把文件写到预期目录之外。
3. 让使用者能判断「当前这份脚本与配置是否就是发布时的内容」。

## 威胁模型

| 威胁 | 可能的后果 | 现有缓解措施 |
| --- | --- | --- |
| 篡改 `config\catalog.json`（改下载地址、哈希或组件定义） | 引导下载并安装攻击者指定的程序 | `config\release-lock.ps1` 记录该文件的 SHA-256，启动时逐项比对；正式版还要求清单与脚本签名有效 |
| 篡改 `config\release-lock.ps1` 本身（改成与恶意文件匹配） | 绕过哈希比对 | 正式版要求发布清单具有与入口脚本相同的代码签名证书指纹；开发版不具备该保护 |
| 中间人攻击（代理、劫持 DNS、伪造热点） | 下载内容被替换 | 仅允许 HTTPS；每次重定向都重新校验域名白名单；固定 SHA-256；Authenticode 发布者校验 |
| 恶意 ZIP（离线包或启动器下载的仓库 ZIP） | 路径穿越写入系统目录、解压炸弹耗尽磁盘 | 限制条目数与解压后总大小；拒绝含 `..` 的路径穿越；拒绝带冒号的文件名；解压目标必须位于允许目录内 |
| 离线包在传输或存放期间被替换 | 植入被替换的安装包 | 离线清单记录安装包与功能载荷的 SHA-256，安装前整体校验，不一致以退出码 `50` 停止 |
| 提权链路被利用（篡改提权命令行、替换被提权的脚本） | 以管理员权限执行其它代码 | 提权命令行按参数逐项引用拼接，仍启动同一根目录下的入口脚本；正式版以 `AllSigned` 运行并要求签名有效 |
| 使用第三方镜像或聚合下载站 | 获得被重新打包的安装程序 | 下载地址只来自目录，且必须命中官方域名白名单；非白名单地址直接拒绝，无法通过修改参数绕过 |

不在威胁模型内的情况：攻击者已经拥有本机管理员权限、内核级恶意软件、硬件植入，以及使用者主动从非官方渠道获取本工具。

## 信任根与校验顺序

信任根分两层：

- 开发构建信任「仓库内容 + `config\release-lock.ps1` 的哈希清单」。
- 正式构建额外信任「公共 CA 代码签名证书」，证书指纹固定写在发布清单里。

启动与安装按以下顺序校验，前一步不通过就不会进入下一步：

1. 入口脚本确认 `config\release-lock.ps1` 存在。
2. 正式版校验入口脚本与发布清单的 Authenticode 签名，要求状态为 `Valid` 且证书指纹与清单一致。
3. 遍历清单登记的每个文件：存在性 → SHA-256；正式版对 `.ps1` / `.psm1` 追加签名与指纹校验。
4. 读取 `config\catalog.json`：下载地址必须是 HTTPS，且主机属于目录声明的官方域名。
5. 下载阶段：每一跳重定向都重新校验域名 → 校验文件大小或大小范围 → 校验 SHA-256 → 校验 Authenticode 发布者。
6. 安装阶段：只把已通过上述校验的文件交给安装程序，安装参数使用目录中的固定值。
7. 离线安装阶段：先整体校验离线清单（安装包与功能载荷的 SHA-256），全部通过后才开始安装。

断点续传不会跳过校验：续传前检查服务器返回的区间起点是否与本地已有长度一致，不一致就丢弃部分文件从头下载；完成后仍走第 5 步的完整校验。校验失败的文件会被清理并自动重新下载一次。

## 发布锁与正式签名构建的要求

- `config\release-lock.ps1` 由 `tools\Build-Release.ps1` 生成，不应手工编辑；手工编辑会让哈希与实际文件不一致。
- 正式发布必须使用 `-Mode Production` 构建，并提供带私钥、含 Code Signing EKU 的公共 CA 代码签名证书指纹。
- 正式构建使用 RFC 3161 时间戳；所有 `.ps1` / `.psm1` 必须由同一证书签名，清单中 `ReleaseKind` 为 `Production`、`CertificateThumbprint` 非空。
- 入口脚本在 `Production` 通道下要求 `AllSigned`，且入口与清单的证书指纹必须与清单记录一致。
- 开发构建（`ReleaseKind = Development`）只做哈希比对，不得作为对外分发物。

## 离线包的信任边界

- 离线 ZIP 本身不带代码签名，它的可信度来自「在哪台机器生成」和「如何传到目标机器」。
- 离线清单中的 SHA-256 只能证明「文件与生成时一致」，不能证明生成者身份；如果生成机器已被攻破，清单会如实记录被替换的文件。
- 建议在可信机器上生成离线包，传输后先核对 ZIP 的整体哈希，再解压到干净目录执行。
- 离线安装不会联网，因此也不会重新获取清单或安装包；发现校验失败只能重新制作离线包。
- `.NET Framework 3.5` 与 DirectPlay 的功能载荷仍由 Windows 组件安装机制与微软包签名保护，本项目不改变该信任链。

## 已知限制

- `SignedLatest` 类型的包（如 VC++ 2015-2022 通过 `aka.ms` 指向最新构建）无法锁定具体版本，只能校验大小范围与 Authenticode 签名；上游发布新版本时文件内容会变化。
- 不检查证书吊销状态（CRL / OCSP），也不判断签名时间戳是否已过期，仅依赖 `Get-AuthenticodeSignature` 的本地判定。
- 功能载荷的哈希由离线清单在打包时记录、安装前校验，但清单是自证的，只能证明「与打包时一致」，不能证明生成者身份；最终仍依赖微软包的签名与 Windows 组件存储。
- 发布清单里的证书指纹由清单自身声明，不是外部固定锚点。如果攻击者能同时替换入口、清单，并用另一张公共 CA 代码签名证书重新签名，正式版仍会通过自校验。正式版主要防御「下载后仅替换部分文件」和未签名篡改，不能替代对下载来源的信任。
- `GameRuntimeLibrary.cmd` 以 `Bypass` 运行启动器，再由启动器拉起菜单。正式版启动器会在拉起前校验入口与发布清单签名，并让菜单以 `AllSigned` 运行；但启动器本身被替换属于分发篡改，不在正式版自校验范围内。
- 无法防御本机管理员：管理员可以替换脚本、证书存储、系统目录或本工具本身。
- 不防御旁路攻击、内核级恶意软件，也不提供网络隔离能力。
- 日志与离线包可能包含本机路径、组件版本与失败信息，对外分享前请自行检查。

## 漏洞报告

请通过仓库 Issue 私下联系维护者，说明受影响的版本、复现步骤、预期与实际结果，以及相关的日志片段。在维护者确认修复方案前，请不要公开可直接利用的细节。
